## 四、本轮必须披露的三处判断

**1. 补上进度库的「写侧」（`progress/store.ts`）。**
排查发现 `PROGRESS_KEY = cpractice:progress:v1` 早已在 `src/app/config.ts` 定义，但模块 1–4 **从未有任何代码往里写**——判分结果只活在组件内存里，刷新即丢，列表页也就无从显示状态。这是任务书要求的「状态标记：读取 localStorage 中已有的答题记录」落不了地的根因。本轮补的是**最小写侧**：一个 persist store + 四个 Renderer 各一行落库钩子，**不新建第二套进度体系**，判分规则一字未动。错题本 / 统计 / 导出导入 / schemaVersion 迁移仍属阶段 5，本轮不做。降级与未判定批次**不写库**，绝不伪造「已通过」。

**2. 修复 `SectionPage` 顶层板块入口占位（改了阶段 1 的已验证文件，理由如下）。**
`SectionPage` 的 `MAP` 用**顶层段**（knowledge / viz / problems）作键，但组件只读 `useParams().section`（那是**子节**名，如 ch09）。结果：顶层入口 `/#/knowledge`、`/#/viz` 没有 `:section` 参数，永远命中通用兜底「后续阶段」，把写好的「阶段 6 / 阶段 7–9 + 待办清单」变成**够不着的死代码**。整站回归第一次点这两个入口即暴露此缺陷（首轮 2 项 FAIL）。改为按 `pathname` 首段定位板块后复跑，16/16 全绿。改动 8 行、不涉 schema / 判分 / 内容，属显示层缺陷修复。

**3. ch09 = 77 而非任务书的 73**，见第二节口径澄清。未改数据，如实呈现。
